**For:** the Hoardini Linux port (Rust).

| # | Type | Change | Port priority |
|---|------|--------|---------------|

## Changes

### 10. No credentials over an https-to-http downgrade  (Security: core)

**Problem:** credentials were kept whenever the host matched, ignoring the scheme. An https playlist listing `http://same-host/seg.ts`, an https audio track on `http://`, or a redirect from https to http on the same host sent the browser's cookies (including `Secure` ones) unencrypted.

**New behavior:** `Cookie` and `Authorization` go to a URL only when both hold:
- its host equals the origin's host (case-insensitive), and
- it is not a downgrade: an https origin only passes them to https URLs. http to https is allowed.

Ports are ignored (cookies are not port-scoped). The origin is the URL the job was given (the HLS master, the video of a video+audio pair, or the first request of a redirect chain). Applies to every request: probes, segments, playlists, audio tracks and redirects. `Referer` and `User-Agent` are unaffected.

**Linux notes:** apply the same rule wherever the port strips credentials for another host, including redirects. With `reqwest`: its default redirect handling drops `Cookie`/`Authorization` only when the host or port changes. That catches https→http on default ports (443→80), but not a same-port downgrade such as `https://h:8080` → `http://h:8080`. `redirect::Policy::custom` can stop or follow a redirect but can't edit headers, so the reliable way is `Policy::none()` and following redirects yourself (up to 10 hops), applying `may_carry_credentials(next, first_url)` at every hop. Segment, playlist and audio requests are not redirects: apply the rule in the code that builds those requests too.

**How to verify:** unit tests in `Tests/HoardiniCoreTests/NetworkTests.swift`. By hand: serve an https playlist whose segments are `http://` on the same host and check the segment requests carry no `Cookie`.

### 11. Session cookies of stale unfinished downloads are dropped  (Security: app)

**Problem:** cookies were cleared from `queue.json` only when a download finished. Paused or failed downloads kept them indefinitely.

**New behavior:** whenever the queue is saved (and once at launch), a paused or failed item added more than 7 days ago loses its cookies. Queued and running items are untouched. Resuming such an item afterwards works when the server needs no login; otherwise send the link from the browser again.

**Linux notes:** same rule for the port's queue file (`~/.local/share/hoardini/queue.json`, mode `0600`, folder `0700`).

**How to verify:** set an item's `added` in `queue.json` to 8 days ago with status `paused` and a `cookies` value, launch the app: the file is rewritten without `cookies` for that item.
