**For:** the Hoardini Windows port (Rust).

## Changes

### 1. Tella.tv videos download as a few-second clip  (Fix)

**Problem:** Downloading `https://www.tella.tv/video/vid_cmv7jic00006702o8gqjz4oa6/view`, a 69-minute video, showed normal progress (slow near the end), but the saved `.mp4` was about 0.8 MB and 12 seconds long. Every segment downloaded correctly. The data was lost when the segments were joined and the tracks merged.

**Root cause:** Tella serves HLS as **fragmented MP4 (CMAF)**: a master playlist with a video-only variant plus a separate `EXT-X-MEDIA:TYPE=AUDIO` rendition. Each media playlist has an `EXT-X-MAP` init segment and then `.cmfv` / `.cmfa` segments. Tella renders each segment on its own, so **every segment's `moof > mfhd` box has `sequence_number = 1`**. The decode timestamps (`tfdt`) are correct and increase.

When those segments are joined (init + seg0 + seg1 + ...) into one file, Apple's AVFoundation treats the repeated sequence number as the same fragment. It reads only the first fragment of each track and ignores the rest. Measured with the same three segments:

| File | Duration AVFoundation reports |
|---|---|
| init + 3 segments, unchanged | 6.0 s (1 segment) |
| init + 3 segments, `mfhd` renumbered 1, 2, 3 | 18.0 s (all 3) |

The broken output had a 6.06 s video track and an 11.9 s audio track, which matches this.

**New behavior:** When an HLS media playlist has an init segment (`EXT-X-MAP`, meaning fMP4), Hoardini renumbers the fragments as it writes each segment to the temp/output file. The first `moof` in the track gets `sequence_number` 1, the next gets 2, and so on, continuing across segment boundaries. Video and audio are numbered **separately**, each starting at 1. MPEG-TS playlists (no `EXT-X-MAP`) are untouched.

**How it works (platform-neutral):**
- An MP4 box is: 4-byte big-endian `size`, then a 4-byte ASCII `type`. If `size == 1`, a 64-bit big-endian size follows (16-byte header). If `size == 0`, the box runs to the end of the data.
- For each downloaded segment's bytes, walk the **top-level** boxes. For each `moof`, walk its children until you find `mfhd`.
- `mfhd` body = 1 byte version + 3 bytes flags + **4-byte big-endian `sequence_number`**. Overwrite those 4 bytes with the running counter, then increment the counter. The data length doesn't change, so no other offsets need fixing.
- Skip any box whose size is malformed or overruns the buffer, and leave the data unchanged rather than failing.
- Keep one counter per track (one for video, one for audio), carried across all segments of that track, in playlist order. Apply it as each segment is written in order, not when it is fetched, because segments are fetched in parallel.

**macOS files touched:** `Sources/HoardiniCore/HLS.swift`. New `FMP4.renumberFragments(_:next:)`, called from `HLSDownloader.write` for fMP4 playlists. Test in `Tests/HoardiniCoreTests/SegmentsTests.swift` (`testRenumbersFragmentsAcrossSegments`).

**Windows notes:**
- The root cause is in the data, not in macOS. Tella's segments are broken the same way for everyone. Whether the Windows build shows the bug depends on how it joins and merges:
  - **Muxing with FFmpeg** (`ffmpeg -i video.mp4 -i audio.m4a -c copy`) or **Media Foundation**: test it. Some demuxers ignore `mfhd` and go by `tfdt` (fine), others don't. Renumbering is cheap and always safe, so **add it anyway**.
  - **Writing your own MP4 muxer:** same advice. Renumber while writing.
- Nothing Mac-specific otherwise.

**How to verify:**
1. Download the Tella URL above (needs the signed `manifest.m3u8?story_id=...&Signature=...` URL, which the browser extension catches from the page).
2. The result should be about **69 min 24 s** long (`total_duration=4163696` ms in the playlist URLs), with video and audio for the whole length. On macOS after the fix: **738 MB**, asset 4163.7 s, video track 4163.7 s, audio track 4163.6 s. Before the fix: 0.8 MB, 12 s.
3. Unit test: build a fake segment `moof(mfhd seq=1, traf) + mdat`, run it through the renumber three times with one counter. You should get sequence numbers 1, 2, 3, the counter should end at 4, and the bytes should otherwise be unchanged.

### 2. Pause and resume for streamed (HLS) videos  (Feature)

**Problem:** Only ordinary file downloads had a Pause button. HLS downloads (Tella, Vimeo and most video sites) couldn't be paused. Quitting the app sent them back to the queue to **start over from zero**.

**New behavior:**
- Every downloading item has a **Pause** button. A paused item has **Resume** (a failed one has **Retry**). Both pick up where they stopped.
- Quitting the app pauses everything that was downloading. On the next launch those items show as **Paused**, not queued, and the user resumes them. This applies to HLS and file downloads alike.
- Resuming an HLS download continues from the **next unfinished segment** of each track. Progress (bar, bytes) starts from what's already on disk.
- If the stream changed between pause and resume (different master URL, different chosen variant, or a different number of segments in any track), the saved progress is thrown away and the download starts over cleanly.
- Pausing during the final video+audio **merge** stops the merge. Resuming skips straight to merging again, since all segments are already on disk.
- **Cancel (X)** on an unfinished item deletes all its leftovers: `.part`, `.hoardini`, and the hidden per-track temp files. It does this only **after** the download task has fully stopped, so nothing gets recreated afterwards.
- Pause → Resume in quick succession reuses the same file name. The app waits for the paused task to fully stop and release its name lock before restarting. Otherwise the resume would see the name as taken and start a new `Name (1).mp4` from scratch.

**How it works (platform-neutral):**

File layout next to the final name `<Final>.mp4`, all in the downloads folder:

| File | When |
|---|---|
| `<Final>.mp4.part` | Single-track stream: segments are appended here directly. Split stream: the merge writes here. |
| `.<Final>.mp4.video.<ext>` / `.<Final>.mp4.audio.<ext>` | Split video + audio stream: one hidden temp file per track. `<ext>` is `mp4` for fMP4 video, `ts` for MPEG-TS video, and `m4a` / `aac` / `mp3` / `ac3` / `ec3` / `ts` for audio. |
| `<Final>.mp4.hoardini` | Resume state (JSON), saved after every batch of segments. |
| `<Final>.mp4.lock` | Name lock held while a download is running (unchanged from before). |

Resume state JSON (`.hoardini`), one entry per track in order: video (or the only track), then audio:
```json
{
  "source": "<master or media playlist URL the job was started with>",
  "variant": "<variant playlist URL chosen in the browser, or absent>",
  "tracks": [
    { "segments": 694, "done": 480, "bytes": 454345484, "sequence": 481 },
    { "segments": 695, "done": 0,   "bytes": 0,         "sequence": 1 }
  ]
}
```
- `segments`: number of segments in that track's media playlist. Used only to detect that the stream changed.
- `done`: how many segments, in playlist order, are fully written to the track file.
- `bytes`: the track file's length after those segments, **including the init segment** (`EXT-X-MAP`) if there is one.
- `sequence`: the next fMP4 fragment number (see fix #1), so the renumbering continues correctly after a resume.

Algorithm for each track, in order:
1. On start, re-fetch and re-parse the playlists as usual. Load `.hoardini` and keep it only if `source`, `variant` and every track's `segments` count match; otherwise start fresh with `done = 0` for all tracks. Save the state immediately.
2. If `done > 0` but the track file is missing or shorter than `bytes`, reset that track to `done = 0` and subtract its old numbers from the progress counter.
3. If `done == 0`, create or empty the track file. Then **truncate the file to `bytes`**. This drops a partly written batch from before the interruption. Seek to the end.
4. If `done == 0` and there's an init segment, download and write it, and set `bytes` to its length.
5. Download segments from index `done` in batches of 6, fetched in parallel and written **in playlist order**. After each batch, update `done`, `bytes` and `sequence` and save the state (atomic write).
6. When every track is complete: for split streams, merge video + audio into `.part` and delete the track temp files. Then mark the download's origin as on macOS (Windows: Mark-of-the-Web, see below), rename `.part` to the final name, and delete `.hoardini`.

Signed URLs such as Tella's CloudFront `Policy`/`Signature` URLs are **not** compared between runs. Only the job's own source URL and the segment counts are. A re-signed segment URL is fine.

**macOS files touched:**
- `Sources/HoardiniCore/HLS.swift`: `HLSTrackState`, `HLSState`, `HLSResumeStore`; `HLSDownloader.run` and `write(...)` rewritten. The segment counter now starts from saved progress.
- `Sources/HoardiniCore/Network.swift`: new `Partial` helper (temp file names; `Partial.remove(final)` deletes `.part`, `.hoardini` and the hidden track files).
- `Sources/HoardiniCore/Remux.swift`: the merge can be cancelled, and a cancelled merge throws "cancelled", not "conversion failed".
- `Sources/HoardiniApp/Models.swift`: `canPause` is true for any downloading item.
- `Sources/HoardiniApp/DownloadManager.swift`: tracks paused tasks still stopping; resume and cancel wait for them; leftovers removed via `Partial.remove`; quitting pauses everything instead of re-queuing HLS.

**Windows notes:**
- Name lock: macOS uses `flock` on `<Final>.lock`. On Windows, use an exclusive file handle (`CreateFile` with `share_mode(0)`, or the `fs4`/`fd-lock` crates). The rule is the same: **a resume must wait for the paused task to release the lock**, or it will pick `Name (1)`.
- Hidden temp files: the leading `.` hides them on macOS but not on Windows. Also set `FILE_ATTRIBUTE_HIDDEN`, or keep the same names and accept that they're visible. Keep the same name pattern so cleanup can find them.
- Atomic state save: write to a temp file, then `MoveFileEx(..., MOVEFILE_REPLACE_EXISTING)` (`std::fs::rename` does this on Windows).
- Cancelling the merge: if the port merges with an FFmpeg child process, kill it on pause and delete the half-written `.part`. If it uses Media Foundation, stop the sink writer.
- Download origin: macOS marks finished files with a quarantine flag. The Windows equivalent is the `Zone.Identifier` alternate data stream (Mark-of-the-Web), applied only to the finished file.

**How to verify:**
1. Start a long HLS download (the Tella URL from #1 is about 700 MB). Pause halfway. The `.hoardini` file should show `done` short of `segments`.
2. Resume. Progress should start from where it stopped, not zero.
3. Kill the app outright (Task Manager; on macOS we used SIGTERM on the CLI). Relaunch: the item shows **Paused**. Resume and it continues.
4. Final file: same size and duration as an uninterrupted download. On macOS: 738,329,923 bytes, 4163.7 s, both times. Only about 20 bytes of creation/modification timestamps differ in the movie header.
5. Cancel (X) on a paused split-stream download: `.part`, `.hoardini` and both hidden track files are gone.
6. Pause, then Resume immediately: it continues into the same file, with no `Name (1).mp4`.

### 3. "Convert to MP4" and "Open" buttons on files that aren't videos  (Fix)

**Problem:** Every finished file not already `.mp4` / `.m4v` / `.mov` (e.g. `.zip`, `.pdf`, `.dmg`) showed a **Convert to MP4** button that made no sense. The **Open** button always used a video "play" icon, even for documents and archives.

**New behavior:**
- **Convert to MP4** appears only for finished **MPEG-TS** files: `.ts`, `.mts`, `.m2ts`. Those are what the converter can remux losslessly (they come from older HLS downloads or the user's own files). Auto-convert after download follows the same rule.
- The **Convert Files…** picker only lets the user choose `.ts` / `.mts` / `.m2ts` files.
- The Open button depends on the file type:
  - **Video** (`.ts` / `.mts` / `.m2ts`, or any extension the OS classes as a movie, e.g. mp4, mov, mkv, webm, avi): play-in-a-rectangle icon, tooltip **"Play"**.
  - **Audio** (the OS classes it as audio: mp3, m4a, wav, flac, …): play-in-a-circle icon, tooltip **"Play"**.
  - **Anything else:** an "open in app" icon (arrow out of a box), tooltip **"Open"**.
  - Nothing changes about what clicking does. It opens the file in the default app.
- The type check uses the converted MP4 if there is one, otherwise the downloaded file. A file with no extension counts as video if it came from an HLS job, otherwise "other".

**How it works (platform-neutral):** look at the file's extension. `ts`/`mts`/`m2ts` → video and convertible. Otherwise ask the OS's type system whether the extension is a movie or audio type.

**macOS files touched:** `Sources/HoardiniApp/Models.swift` (`DownloadItem.convertible`, `canConvert`, `kind`), `Sources/HoardiniApp/Views.swift` (Open button icon and tooltip by kind; picker file types).

**Windows notes:**
- macOS uses `UTType` (`.movie` / `.audio`). On Windows, read `HKEY_CLASSES_ROOT\.<ext>` → `PerceivedType` (`video`, `audio`), or call `AssocQueryString` with `ASSOCSTR_PERCEIVEDTYPE`. A small built-in extension list as a fallback is fine.
- Icons: macOS uses SF Symbols `play.rectangle`, `play.circle` and `arrow.up.forward.app`. Use the closest equivalents in the Windows UI's icon set (e.g. Segoe Fluent Icons: Video / Play / OpenInNewWindow).

**How to verify:** download a `.zip` or `.pdf`: there's no convert button, and the Open icon is the arrow-out-of-box with tooltip "Open". Download an `.mp3`: circle play icon, tooltip "Play". Use **Convert Files…** on a `.ts`: it converts, and the convert button is gone afterwards.

### 4. Facebook videos: full video in your choice of quality, instead of tiny pieces  (Fix + Feature)

**Problem:** On a Facebook video page (test: `https://www.facebook.com/hlaccelerator/videos/2124866271452320`, 2 h 7 min 50 s), the extension popup listed three "File · 0.4 MB / 0.2 MB / 1.6 MB" entries. Facebook's player fetches **pieces** of separate video-only and audio-only MP4 files, using `?bytestart=…&byteend=…` query parameters. The extension treated each piece as a downloadable file. The suggested name was also page clutter ("HL AcceleratorVerified account was live.") instead of the video title.

**What Facebook actually serves** (in the page's own `<script type="application/json">` data, for a page loaded directly):
```
"videoDeliveryLegacyFields":{
   "dash_manifest_xml_string":"<?xml …><MPD>…</MPD>",   // DASH: separate video-only + audio-only MP4s
   "dash_manifest_url":"…",
   "browser_native_sd_url":"https://video…fbcdn.net/…",   // single complete MP4, video + audio
   "browser_native_hd_url":"https://video…fbcdn.net/…",   // single complete MP4, video + audio
   "id":"2124866271452320"                                 // the video ID
}
```
- `browser_native_hd_url` was a 184 MB complete MP4 (H.264 + AAC, range requests supported), but only **640×360**, despite the name.
- The DASH manifest had **720p**, 360p and 144p video-only representations (H.264 `avc1`) plus one AAC audio-only representation (`mp4a.40.5`). Each `<BaseURL>` is a **complete file**, no byte range needed, and accepts range requests.
- The title is in another JSON block: `"title":{…,"text":"LIVE NOW: Create AI Agents with Grok Bot"}`, a short way after `"id":"<video id>"`.
- Fetching the page from the extension's background script does **not** work. Facebook omits all of this unless the request is a real page navigation (`Sec-Fetch-Mode: navigate`), which extensions can't fake. So the data is read **inside the tab**.
- First version (0.4.2) only scanned the page's `<script>` elements when the popup opened. **That failed in the user's logged-in browser** at `https://www.facebook.com/watch/live/?ref=watch_permalink&v=2124866271452320`. When you click through to a video, Facebook loads its data through background GraphQL requests, and it removes some inline data blocks after using them. Version 0.4.3 collects the data continuously from page start instead (below).

**New behavior (extension):**
1. Network detection ignores any request whose URL has a `bytestart` or `byteend` query parameter (pieces of a DASH file). Those "0.4 MB" entries are gone.
2. **`extension/fb.js`**, a content script registered in the manifest for `https://*.facebook.com/*` with `"run_at": "document_start"` and `"world": "MAIN"` (the page's own JS world, so it can watch the page's network calls). It keeps `window.__hoardiniFB = { videos: {<id>: {hd, sd, mpd}}, titles: {<id>: title} }` and fills it from three sources:
   - every `<script>` already in the page when it starts;
   - every `<script>` added later (a `MutationObserver` on the document, read **as it's added**, before Facebook can remove it);
   - the response text of every `XMLHttpRequest` and `fetch` whose URL contains `/api/graphql`, `/ajax/` or `graphql` (a clone of the response is read; the page's own response is untouched).

   Field extraction does **not** depend on field order:
   - Regex `"(browser_native_sd_url|browser_native_hd_url|dash_manifest_xml_string|progressive_url|manifest_xml)":"STR"`. The first three are the older layout. `progressive_url` / `manifest_xml` are Facebook's newer `videoDeliveryResponseFragment` layout (`progressive_urls: [{progressive_url, metadata: {quality: "HD"|"SD"}}]`, `dash_manifests: [{manifest_xml}]`), which may be what logged-in sessions get. For `progressive_url`, the quality is the first `"quality":"(HD|SD)"` within 300 characters after it. Per video, the **first** value seen for each of hd/sd/mpd is kept.
   - `STR` = `((?:[^"\\]|\\.)*)` (a JSON string body). Each captured string is unescaped as JSON.
   - Fields with no video ID found nearby are stored under `"?"`. On a video page whose own ID wasn't seen, the popup uses the `"?"` entry instead.
   - The match belongs to the video whose `"id":"(\d+)"` comes **first after the match, within 5,000 characters** (in Facebook's data, the `id` closes the object these fields are in). Otherwise it's the **last `"id":"(\d+)"` within the 2,000 characters before** the match.
   - Title: `"title":\{(?:[^{}"]|"STR")*?"text":"STR"`, assigned to the last `"id":"(\d+)"` within the 300 characters before it. The first title per ID wins.

   When the popup opens, it injects `fb.js` into the tab again (a no-op if it's already running). This covers tabs opened before the extension was installed or reloaded. Then it reads `window.__hoardiniFB` in the page's world, after re-scanning the current `<script>` elements.
3. Video ID from the address bar: `?v=<id>`, or `/videos/<id>`, `/videos/<slug>/<id>`, `/reel/<id>`, `/watch/<id>`. When the address bar has a video ID, offer **only** that video. If its data hasn't been seen, show nothing plus the hint below, rather than a different video from the feed.
4. The popup shows **one "Facebook video" row** with a quality menu:
   - First, one entry per **DASH video height**, best first (e.g. **720p**, 360p, 144p). Each uses the highest-bandwidth representation at that height, paired with the highest-bandwidth AAC audio. Only video codecs `avc1`/`hvc1`/`hev1` and audio `mp4a` are offered, because those can be merged into MP4 without re-encoding. VP9/AV1/Opus are skipped.
   - Then **"HD file"** and **"SD file"** (the `browser_native_*` single files) as fallbacks.
   - The default is the first entry, i.e. the best DASH quality.
   - The size shown is video plus audio, from a `Range: bytes=0-0` request to each (`Content-Range` total). It updates when the quality changes.
   - The suggested name is the video's title.
5. If the address bar shows a Facebook video but its data wasn't found (e.g. the tab was open before the extension was installed or reloaded), the popup says: *"Hoardini has not seen this Facebook video's details yet. Reload the page, then reopen this popup."*
6. The download message to the native host gains an **`audio`** field: the audio-only URL, or empty. `kind` stays `"file"`.

**New behavior (core / app): "pair" job.** A job with `kind: "file"` and a non-empty `audio` URL:
1. Final name: the given filename with a trailing `.mp4/.m4v/.mov` stripped, sanitized, plus `.mp4`. Claim it with the usual name lock.
2. Probe both URLs (`Range: bytes=0-0`) to get both sizes. Progress total = video + audio bytes.
3. Download **both files at the same time**, each as an ordinary segmented, resumable file download (8 connections, `.part` + `.hoardini` resume state, as in SPEC.md), into hidden track files next to the final name:
   - `.<Final>.mp4.video.mp4` (and its `.part`, `.hoardini`, `.lock` while downloading)
   - `.<Final>.mp4.audio.mp4` (same)
   These names are used exactly as given. They deliberately skip the filename sanitizer, which would strip the leading dot.
4. If a track file already exists **with no `.hoardini` next to it**, an earlier run finished it. Reuse it and count its size as done.
5. Merge video + audio into `<Final>.mp4.part` without re-encoding (same merge as the HLS split-audio path), mark the download origin, rename to `<Final>.mp4`, and delete both track files.
6. Pause/resume and quit/relaunch work through each track's own resume state. Cancel deletes everything via the same leftover cleanup as #2: `.part`, `.hoardini` and any hidden `.<Final>.mp4.video.*` / `.audio.*` files.
- HLS jobs ignore `audio` (HLS finds its own audio track in the master playlist).

**Measured on macOS (test video above):**

| Choice | Result |
|---|---|
| 720p (DASH pair) | 318.5 MB video + 63.2 MB audio → **382,251,183-byte MP4, 1280×720, 7670.33 s**, video and sound full length. Merge ≈ 5 s. Killed after 2 s and resumed: same result. |
| HD file | 184,212,585 bytes, **640×360**, 7670.33 s, video + sound. Downloaded in ≈ 5 s. |

**macOS files touched:**
- `extension/background.js`: skips `bytestart`/`byteend` pieces; passes `audio` to the native host.
- `extension/fb.js` (new): the Facebook data collector described above.
- `extension/popup.js`: `facebookItems` (injects and reads `fb.js`'s store), `facebookVideoID`, `dashChoices`, `fileSize`; quality menu for `choices`; the "reload the page" hint.
- `extension/manifest.json`: `content_scripts` entry for `fb.js` (MAIN world, document_start, facebook.com only); version **0.4.4** (0.4.3 = collector, 0.4.4 = newer layout).
- `Sources/HoardiniCore/Job.swift`: `JobRequest.audio`, `validAudio` (nil for HLS jobs).
- `Sources/HoardiniCore/Pair.swift` (new): `PairDownloader`.
- `Sources/HoardiniCore/Downloader.swift`: internal `exactName` to download to a given name as-is.
- `Sources/HoardiniApp/DownloadManager.swift`: starts a `PairDownloader` when the job has `audio`.
- `Sources/hoardini/main.swift`: new `--audio <url>` flag. `Sources/hoardini-host/main.swift`: forwards `audio` (as `--audio` when there's no app).

**Windows notes:**
- **The extension is the same code for both platforms.** The Windows port just needs to load the updated `extension/` folder. The one contract change is the new `audio` field in the native message.
- The native host (Windows registry entry under `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.hoardini.host`) must pass `audio` through to the app/CLI unchanged. Accept it as an optional string; older extensions won't send it.
- Merge: use the same merge as the HLS split-audio path. With FFmpeg: `ffmpeg -i video.mp4 -i audio.mp4 -map 0:v:0 -map 1:a:0 -c copy -movflags +faststart out.mp4`. Facebook's DASH files are fragmented MP4 with a `sidx` index. FFmpeg handles that fine; check Media Foundation if it's used instead.
- Hidden track files: set `FILE_ATTRIBUTE_HIDDEN` as in #2. Keep the names so cleanup and resume can find them.

**How to verify:**
1. Load the updated extension (version 0.4.4) and **reload any Facebook tabs that were already open**. Open the test video, either directly or by clicking to it from Facebook, and open the Hoardini popup.
2. There's **one** row, "Facebook video", titled "LIVE NOW: Create AI Agents with Grok Bot", with a menu: 720p, 360p, 144p, HD file, SD file. No 0.4/0.2/1.6 MB entries.
3. Download 720p: about 382 MB, 1280×720, 2:07:50 with sound.
4. Pause halfway, resume: it completes with the same result. Cancel instead: no hidden `.…video.mp4*` / `.…audio.mp4*` files left in Downloads.
5. While logged in, click to a video from the feed or the Watch tab (not a direct load): the row should still appear. Only a tab opened before the extension was (re)loaded should show the "Reload the page" hint.

### 5. Security hardening of today's changes  (Security)

Reviewed everything added in 1–4 before release. Fixed:

| # | Risk | Fix | Port it as |
|---|---|---|---|
| a | **Crash from a hostile stream** (fix #1). MP4 box sizes come from the server. A 64-bit size near `UInt64.max` made the Swift `Int(...)` conversion trap, and `offset + size` could overflow. | Compare sizes as **unsigned 64-bit** against the bytes remaining (`size >= header && size <= end - offset`) **before** converting or adding. Malformed boxes stop the scan and leave the data unchanged. | In Rust: `u64` maths with `checked_add`, or compare against `remaining` first. Never `as usize` an unchecked server value, never index without a bounds check. |
| b | **Crash from a corrupt resume file** (#2). `.hoardini` lives in Downloads and anything can edit it. A negative `bytes` made `UInt64(bytes)` trap during truncation. | Load the state only if, for every track, `0 <= done <= segments`, `bytes >= 0` and `sequence > 0`; otherwise start over. | Same checks when deserialising (`serde`), and treat any parse error as "no saved state". |
| c | **Cookie leak** (#4). The browser attaches cookies for the **video** URL's host. The pair download sent the same `Cookie`/`Authorization` headers to the **audio** URL, which could be on another host. | Audio requests (probe and download) drop `Cookie` and `Authorization` when the audio host differs from the video host. This is the rule already used for redirects and HLS segments. | Same rule anywhere a job's headers are reused for a second URL. |
| d | **Untrusted page data** (#4). `fb.js` runs in Facebook's **page world**, so Facebook's own scripts (or anything else running in the page) can rewrite `window.__hoardiniFB`. The popup would then have offered, size-probed and sent any URL. | The popup treats what it reads as data: it must be an array of objects, and only strings are kept (title capped at 300 characters, manifest at 1 MB). **Every offered URL (HD, SD, each DASH video and audio) must be `https:` on a `*.fbcdn.net` host**, or it's dropped. Size probes only go to those URLs, without cookies. | The extension is shared, so nothing extra is needed. The host/app should keep validating `http(s)` URLs as before. |
| e | Popup could be broken by a malformed store (same cause as d). | The checks in d also stop the popup failing on bad data. | Shared extension. |

- Filenames: Facebook titles and every other suggested name still go through the existing sanitiser (invisible/control characters removed, `/` and `:` replaced, leading dots stripped). Only the internal hidden track names skip it, and those are built from the already-sanitised final name.

- Finished files are still marked with their download origin (macOS quarantine; Windows: Mark-of-the-Web), including HLS resumes and merged pairs. Hidden temp files aren't, and they're deleted.
- No signed URLs, cookies or personal data are in the repo or these notes.

- Hostile box sizes (`UInt64.max`, `0x7ffffffffffffff0`, `0xfffffff0`, truncated header, size < header, short `mfhd`): no crash, data unchanged. Normal segments still number 1, 2, 3.

### 6. Extension stopped working after deleting the download  (Fix: installer + README)

**Problem:** The README said the downloaded zip and folder could be deleted after installing. On a Brave install, deleting the folder broke the extension. A browser loads an **unpacked** extension from whatever folder is chosen in "Load unpacked" and keeps reading it from there. The installer copies the extension to a permanent location (`~/Library/Application Support/Hoardini/extension`), but that folder is hidden. The instructions only mentioned Chrome and never warned against picking the `extension` folder **inside the download**, which is the easy one to find.

Second gap: the installer registered the native-messaging helper only for Google Chrome (`~/Library/Application Support/Google/Chrome/NativeMessagingHosts/com.hoardini.host.json`). Brave, Edge, Chromium and Vivaldi each have their own folder.

**New behavior (installer `install.sh` in the release zip, and `scripts/install-chrome.sh` for source builds):**
- The helper manifest is written for Chrome as before. It's also copied into `<browser>/NativeMessagingHosts/` for each of `BraveSoftware/Brave-Browser`, `Microsoft Edge`, `Chromium` and `Vivaldi` **if that browser's support folder exists** (no folders are created for browsers that aren't installed).
- The permanent extension path is put on the clipboard (`pbcopy`).
- The final message gives the per-browser extensions page (`chrome://`, `brave://`, `edge://extensions`) and the exact keystrokes (Load unpacked → ⌘⇧G → ⌘V → Return → Select). It also warns: **don't pick the `extension` folder inside the download.**
- README install step 3 says the same, and adds a recovery note: if the extension stopped working after deleting the download, remove it and load it again from the permanent path. Run `install.sh` from a fresh download first if that folder is gone.

**Windows notes:**
- Same root cause on Windows: an unpacked extension must be loaded from a **permanent** folder (e.g. `%LOCALAPPDATA%\Hoardini\extension`), never from the extracted download. Have the installer copy it there, put the path on the clipboard (`Set-Clipboard` / `clip`) and say so explicitly.
- Native-messaging registration on Windows is a registry key per browser, each with default value = full path to the host manifest JSON:
  - Chrome: `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.hoardini.host`
  - Edge: `HKCU\Software\Microsoft\Edge\NativeMessagingHosts\com.hoardini.host`
  - Chromium: `HKCU\Software\Chromium\NativeMessagingHosts\com.hoardini.host`
  - Brave reads Chrome's key on Windows; registering under `HKCU\Software\BraveSoftware\Brave-Browser\NativeMessagingHosts\com.hoardini.host` as well does no harm.
- The extension ID is fixed by the `key` in `extension/manifest.json`, so one `allowed_origins` entry (`chrome-extension://lllcaffncpkgndgbilnefakajeambdib/`) works for every browser.

**How to verify:** install from the zip, load the extension using the clipboard path, delete the downloaded zip and folder, restart the browser. The extension still loads and "Download with Hoardini" still reaches the app.
